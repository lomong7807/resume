## 3. 프로젝트별 상세

### 3.1 Rainbow Monitoring (데이터센터 모니터링 솔루션)

| 항목 | 내용 |
|---|---|
| 기간 | 2025.06 ~ 진행 중 |
| 소속 | 라인업코리아 솔루션연구소 |
| 역할 | 프로젝트 리드 (설계·개발, 배포 파이프라인, 개발 프로세스 정립). 2026년 6월 이후 단독 개발 |
| 사용 기술 | Java 17, Spring Boot 3, Spring Security, JPA, QueryDSL, PostgreSQL, Thymeleaf, Three.js, Apache POI, Apache MINA SSHD, Jenkins, GitLab, Prometheus, Claude Code |

#### 프로젝트 설명

대학 고객사 약 30곳에서 사용하는 데이터센터 모니터링 웹입니다. 서버실, 랙, 장비를 3단 계층으로 등록·관리하고(고객사당 장비 1~30대), 별도의 수집 프로그램이 SNMP로 모아 적재한 네트워크·스위치 장비 데이터와 상태 정보를 대시보드로 보여줍니다. 이 웹의 설계와 개발을 리드하면서 배포 파이프라인 구성과 개발 프로세스 정립까지 맡았습니다. 2025년 하반기 프로토타입과 요구 정리를 거쳐 2026년 1월부터 본 개발을 진행하고 있습니다.

#### 배경과 문제

기존 사내 NMS는 화면이 전부 영어였고 각 데이터가 무엇을 뜻하는지 분명하지 않았으며, 메뉴를 눌러 들어가야만 정보를 볼 수 있었습니다. 개발을 진행하면서 더 근본적인 문제도 발견했습니다. 장비 유형별로 상태 데이터의 출처가 달라 대시보드와 목록, 상세 화면이 서로 다른 장비 수를 보여주고 있었고, 팀은 "SNMP로 장비 상태를 확인한다"고 알고 있었지만 화면에 표시되는 '정상'은 실제로는 ICMP 응답 여부였습니다. 이 차이를 분석 문서로 정리해 공유했습니다.

#### 기술 선택과 근거

- **상태 판정 기준 단일화**: 판정 기준을 기준 문서 한 곳에 정의하고 모든 화면이 같은 경로를 따르게 했습니다. 화면마다 기준이 다르면 같은 장비가 화면마다 다른 상태로 보이기 때문입니다. 대신 상태를 SQL에서 바로 필터링할 수 없게 되어 Java 쪽에서 페이징하는 비용을 감수했고, 장비 수가 늘어나면 재검토한다는 조건을 문서에 남겼습니다.
- **장비와 에이전트 데이터 매칭을 IP 기준으로**: 에이전트가 수집한 장비명과 웹에 등록한 장비명이 다를 수 있어 이름은 매칭 조건에서 빼고 IP만 사용했습니다. 매칭은 5분 주기로 반복 실행해도 결과가 같도록(idempotent) 동기화합니다.
- **WAR + 외부 Tomcat**: 고객사 운영 환경의 배포 방식에 맞춘 구성입니다.
- **CI와 배포를 분리하되 같은 gradle 명령 사용**: MR 검증 CI와 배포 파이프라인을 분리했지만 빌드·테스트는 동일한 gradle 명령을 쓰게 했습니다. 두 파이프라인이 다른 명령을 쓰면 "CI는 통과했는데 배포에서 빌드가 깨지는" 상황이 생깁니다.
- **배포 파이프라인에만 대기 시간을 둠**: 배포는 여러 MR을 연달아 머지하는 상황이라 이벤트를 묶을 필요가 있지만, CI는 push 간격이 분 단위라 묶을 이유가 없습니다.
- **CI 인증에 개인 토큰 대신 프로젝트 액세스 토큰**: 개인 토큰을 쓰면 발급자가 퇴사할 때 CI가 멈춥니다.
- **AI 협업 워크플로우**: 커밋 컨벤션 문서와 MR 템플릿을 만들고 이를 강제하는 Claude Code hook, 프로젝트 rules·skill을 구성했습니다. 스펙 문서를 먼저 쓰고 구현한 뒤 여러 관점으로 검증하는 흐름입니다.

#### 수행 내용

- 서버실·랙·장비 3단 계층 등록·관리 화면과 상태 대시보드 개발
- 대시보드, 장비, 랙, 서버실, 사용자, SSH, 자산 도메인을 같은 계층 구조로 백엔드 구성
- 브라우저 SSH 터미널, 서버실 3D 배치 편집기, 엑셀 일괄 등록, 모니터링 지표 노출(Actuator, Prometheus) 구현
- 배포 파이프라인: 빌드·테스트, WAR 전송, Tomcat 재기동, 헬스체크, 실패 시 최신 백업 WAR로 자동 롤백, 변경 내역 수집, Notion 배포 이력 기록, Teams 알림
- MR 검증 CI: 빌드·테스트와 Gemini API 기반 AI 코드 리뷰를 MR 코멘트로 게시

#### 업무 성과

- 화면마다 다르게 나오던 장비 상태 판정을 기준 문서 하나로 통일해, 대시보드·목록·상세가 같은 장비 수와 상태를 보여주게 했습니다.
- 팀이 "SNMP 상태 확인"으로 알고 있던 판정이 실제로는 ICMP 응답이었던 점을 분석 문서로 밝혀, 기능 설명과 화면 표시 기준을 실제 동작에 맞췄습니다.
- 배포를 Jenkins 파이프라인으로 자동화해, 머지 이후 사람이 개입하지 않아도 헬스체크·롤백·이력 기록·알림까지 끝나게 했습니다.
- MR마다 빌드·테스트와 AI 코드 리뷰가 자동으로 달리게 해, 리뷰 없이 머지되는 변경이 없도록 했습니다.
- 커밋 컨벤션·MR 템플릿과 이를 강제하는 훅을 도입해 팀원이 같은 방식으로 개발하게 했습니다.

### 3.2 Rainbow 수집기(C) 인수 · 안정화

| 항목 | 내용 |
|---|---|
| 기간 | 2026.08 |
| 소속 | 라인업코리아 솔루션연구소 |
| 역할 | 인수 판단, 결함 분석, 수정 단독 수행 |
| 사용 기술 | C, CMake, PostgreSQL, ICMP, HMAC-SHA256, AES-GCM, Claude Code |

#### 프로젝트 설명

외주로 개발된 장비 상태 수집기(C로 작성된 클라이언트·서버·상태 확인 프로세스 3종)를 인수해 운영 가능한 수준으로 안정화했습니다. Java가 주력이라 C에 익숙하지 않았지만 AI로 코드베이스의 구조와 데이터 흐름을 분석해 결함을 파악하고 직접 수정했습니다.

#### 배경과 문제

1월 전달본을 검토해 지적한 12건 중 3월 최신본에서 고쳐진 것은 1건, 부분 수정 1건이었고 나머지는 그대로였습니다. 특히 실제 장애를 냈던 결함을 새로 추가된 컴포넌트가 그대로 반복하고 있었습니다. 개별 결함의 문제가 아니라 지적 사항이 개발 과정에 반영되지 않고 있다고 판단해 인수를 결정했습니다. 작업에 앞서 개발 DB와 설정 파일을 대조해 지금 운영 중인 버전이 무엇인지부터 확정했습니다.

#### 기술 선택과 근거

- **C 유지 (언어 전환하지 않음)**: 고객사 장비에 설치되는 클라이언트가 91KB 단일 바이너리에 런타임 의존성이 없다는 점은 설치 환경을 가리지 않아야 하는 제품에서 포기하기 어려운 이점입니다. 이번 작업의 목적은 언어 전환이 아니라 코드 소유권을 내부로 가져오고 안정화하는 것이었습니다.
- **검증 로직을 수신 진입점 한 곳으로 집중**: 우선순위가 높은 결함 3건(인증 없는 패킷으로 서버가 중단, 검증 없는 길이 값으로 메모리 밖을 읽은 뒤 DB에 적재, 클라이언트 소유권 미확인)을 처리하면서 검증을 메시지 처리 진입점 한 곳에 모았습니다. 케이스마다 흩어 놓으면 메시지 유형을 추가할 때 또 빠집니다. 수정은 전부 TDD로 진행했습니다.
- **중복 기동 방지에 PostgreSQL advisory lock**: 지켜야 할 대상이 데이터 행이 아니라 프로세스 자리이고 lock 수명이 데몬 수명(수 시간에서 수 일)이라 트랜잭션 lock은 맞지 않았습니다. SELECT FOR UPDATE를 장기 유지하면 VACUUM이 오래된 행을 정리하지 못해 테이블이 부풀고 XID 소진 위험이 생깁니다. flock이나 pidfile은 같은 호스트에서만 유효한데 충돌 자원이 DB라 맞지 않았습니다.
- **CMake 기반 재현 가능한 빌드**: 빌드 대상에서 제외한 항목은 사유와 함께 문서로 남겼습니다.

#### 수행 내용

- 지적 사항 12건의 처리 현황 대조, 인수 판단 근거 정리, 운영 중인 버전 확정
- 안정성 결함 3건 TDD 수정, advisory lock 기반 중복 기동 방지 구현
- 상태 표시가 5초 주기로 바뀌던 현상의 원인 규명: 상태 확인 프로세스 2개가 동시에 떠 서로 상태를 덮어쓰고 있었습니다. 실제 운영에서 관측된 장애입니다.
- CMake 재현 빌드 구성

#### 업무 성과

- 외주에 의존하던 수집기 코드를 인수해 내부에서 직접 수정하고 빌드할 수 있게 했습니다.
- 인증 없는 패킷 하나로 서버가 중단되던 결함을 포함해 우선순위 높은 안정성 결함 3건을 수정하고 테스트로 고정했습니다.
- 수집 프로세스 2개가 동시에 떠 상태가 5초마다 뒤바뀌던 운영 장애를 advisory lock으로 재발하지 않게 했습니다.
- 빌드를 CMake로 정리해 어느 환경에서든 같은 결과물을 재현할 수 있게 했습니다.

### 3.3 서울기록원 기록관리시스템 웹 취약점 조치

| 항목 | 내용 |
|---|---|
| 기간 | 2026.08 |
| 소속 | 라인업코리아 (서울기록원 영구기록물관리시스템) |
| 역할 | 웹 애플리케이션 영역 취약점 조치 전담, 단위테스트 78건 작성 |
| 사용 기술 | Java 8, Spring MVC, Spring Security, JUnit, Claude Code |

#### 프로젝트 설명

외부 보안 진단에서 지적된 항목 중 웹 애플리케이션 영역 5건(불충분한 인가 2건, 경로 추적, 파일 업로드, Stored XSS)을 조치했고, 단위테스트 78건을 함께 작성했습니다. 조치 후 재진단을 통과했습니다.

#### 배경과 문제

지적된 항목 대부분이 UI에서 버튼만 숨기고 서버는 막지 않는 패턴이었습니다. 게시판은 여러 컨트롤러가 각자 권한 검사를 갖고 있으면서도 그 결과를 버튼 숨김에만 쓰고 있어, API를 직접 호출하면 권한 없이 저장이 되었습니다.

#### 기술 선택과 근거

진단보고서의 권고를 그대로 따르지 않고 근거를 들어 다르게 처리한 지점이 세 곳 있습니다.

- **Stored XSS: 입력 이스케이프(권고) 대신 출력 인코딩**. 렌더링이 안전하다면 저장값을 이스케이프해도 보안에 도움이 되지 않고, '&' 같은 평범한 문자가 깨지며, 수정 화면에서 원문을 복구할 수 없기 때문입니다. 실제 원인은 벤더 JS가 내용이 비어 있으면 innerHTML 경로를 타는 분기였고, textContent로 수정했습니다. 같은 방식의 바인딩을 전부 확인해 서버가 HTML을 주입하는 곳이 한 곳뿐임을 확인한 뒤 적용했습니다.
- **파일 업로드: 차단목록 대신 허용목록**. jsp, jspx, jspf 같은 변종이 계속 생기기 때문에 차단목록은 하나만 빠뜨려도 뚫립니다. 허용 확장자는 개발 DB에 실제로 저장된 첨부 파일의 확장자를 조사해 정했습니다.
- **경로 추적: 문자 필터링 대신 정규화 후 차단**. 정상 요청에도 슬래시와 점이 들어가므로 문자 필터링은 정상 기능을 깨뜨리거나 우회를 허용하거나 둘 중 하나가 됩니다.

그 밖의 판단은 다음과 같습니다.

- **인가 검사 기준을 요청 URL 문자열이 아니라 Spring 라우팅 결과로**: 요청 문자열을 그대로 비교하면 실제 라우팅 결과와 달라집니다. 이 과정에서 우회 경로 3종(퍼센트 인코딩, path parameter, 더블 슬래시)을 직접 찾아 차단하고 각각을 테스트로 고정했습니다.
- **과차단 방지를 테스트로 고정**: 공격 케이스만 고정하면 정상 업무가 막히는 것을 잡을 수 없어, 한글 파일명(NFC/NFD 조합)이나 이름에 점이 여러 개 들어간 정상 업무 파일이 통과하는 것도 함께 테스트로 남겼습니다.

#### 수행 내용

- 인가 검사 재구성과 우회 경로 3종 차단, 파일 업로드 허용목록 전환, 경로 추적 정규화 차단, Stored XSS 출력 인코딩 처리
- 연쇄 문제 수정: 403을 반환하도록 바꾸자 공통 예외 핸들러가 이를 삼켰고, 그것을 고치자 프론트 공통 ajax 래퍼가 403을 success 콜백으로 넘겨 화면에 아무 표시도 되지 않았습니다. 세 지점을 모두 수정했습니다.

#### 업무 성과

- 지적된 웹 취약점 5건을 모두 조치해 재진단을 통과했습니다.
- API 직접 호출로 권한 없이 저장되던 경로를 서버 측 인가로 막고, 진단에 없던 우회 경로 3종까지 찾아 차단했습니다.

- 요청받지 않은 취약점 2건을 추가로 발견해 보고했습니다.

### 3.4 서울기록원 기록관리시스템 정리기술 모듈 개발

| 항목 | 내용 |
|---|---|
| 기간 | 2026.02 ~ 진행 중 (데이터 추출 기능은 검수 대기) |
| 소속 | 라인업코리아 (서울기록원 영구기록물관리시스템) |
| 역할 | 정리기술 모듈 설계·개발 담당. 대상 시스템은 2017년부터 운영된 약 20만 LOC 규모의 레거시 |
| 사용 기술 | Java 8, Spring Boot 1.5, Oracle 19c, MyBatis, JPA, QueryDSL, Apache POI(SXSSF), Gradle 멀티모듈, Claude Code |

#### 프로젝트 설명

2017년부터 운영된 약 20만 LOC 레거시 기록관리시스템의 고도화를 담당했습니다. 기존 "전거 관리" 메뉴 그룹을 "정리 기술(Arrangement & Description)"로 재편하고, 개발한 화면들을 그 아래로 모아 전용 역할을 부여했습니다. 화면은 전거 등록부(기존), 전거 일괄 등록, 신청 관리, 철·건 일괄 수정, 데이터 추출로 구성되며, 승인 관리와 헤더 알림으로 이루어진 승인 인프라를 네 화면이 공유합니다.

#### 배경과 문제

업무프로세스 정의서 두 건이 동일하게 "대량 메타데이터 수정은 개발자가 직접 SQL 쿼리로 처리하고 있다"고 적고 있었습니다. 목표는 세 가지였습니다. 개발자 의존도 제거, 현재값과 변경값을 diff로 미리 보여 주어 실수 방지, 검증에서 미리보기를 거쳐 확정에 이르는 3단계로 잘못된 수정 차단입니다.

데이터 추출은 성격이 조금 다른 문제였습니다. 약 44만 건 규모의 기록물 DB에서 담당자는 상세 조건이 걸린 데이터 추출을 웹에서 스스로 할 수 없어 개발자에게 구두나 문서로 요청하고, 개발자가 쿼리를 작성해 파일로 전달하는 흐름이었습니다. 담당자가 생각한 데이터와 개발자가 만든 데이터가 달라 재작업이 반복됐습니다. 실제 사례에서는 요청서에 적히지 않은 조건 3가지(기간 조건 불필요, 분권 포함, 분권을 부모 철 기준으로 정렬)가 뒤늦게 드러나 쿼리를 두세 번 다시 고쳤습니다. 그때그때 만든 일회성 SQL이 여러 개 남아 있었습니다. 결국 필요한 것은 검색 기능이 아니라 추출 기능이었습니다.

#### 기술 선택과 근거

**공통 승인 파이프라인**

- **신청, 승인, 반영의 3단계 분리**: 신청 단계에서는 신청 내용만 저장하고 실제 INSERT/UPDATE는 승인 시점에 단일 트랜잭션으로 처리해 실패 시 전체가 롤백되게 했습니다.
- **승인 유형별 처리기 연결**: 승인 유형을 enum으로 정의해 유형별 처리기를 연결하고, 신규 유형을 추가할 때 분기 한 줄로 끝나도록 했습니다. 순환 의존은 지연 주입(@Lazy)으로 피했습니다. 세 기능(일괄 등록, 일괄 수정, 데이터 추출)에 재사용해 검증했습니다.
- **승인 시점 optimistic lock**: 신청 시점의 값과 승인 시점의 현재값을 비교해 충돌을 검출합니다. 충돌은 toast로 하나씩 알리지 않고 전부 모아 표 모달로 한 번에 보여 줍니다. 일괄 등록과 일괄 수정이 공유합니다.
- **대량 처리 대응**: 3,000행 상한을 두고, Oracle IN 절의 1,000개 제한은 900개 단위로 나눠 조회하며, 식별자 자릿수가 섞여 있어 자릿수에 관계없이 매칭되게 했습니다.
- **메뉴·권한 등록 SQL을 환경 독립적·idempotent하게 작성**: 내부 ID를 하드코딩하지 않고 프로그램 식별자로 동적으로 찾게 했습니다. 개발 DB와 운영 DB의 차이에 안전해야 했기 때문입니다.

**데이터 추출**

- **모든 추출을 백그라운드 잡으로 통일**: 설계 인터뷰에서 예상 소요 시간에 따라 동기와 비동기로 분기하는 안 대신 전부 백그라운드로 통일하자고 제안해 확정했습니다. 분기 로직과 이중 경로가 사라지고, 앱에 이미 있던 비동기 스레드풀과 알림 시스템을 재사용할 수 있기 때문입니다. 소량 추출은 수 초 내에 끝나 알림 폴링 주기(최대 60초) 안에 도달합니다. 실제로 이후 동기로 남겨 둔 건수 확인 구간이 대용량 테이블 full scan으로 60초 statement timeout에 걸리는 일이 있었습니다.
- **상한 20만 건**: 계산으로 유도한 값이 아니라 실제 요청 사례 약 11.5만 건의 약 2배를 여유로 잡은 운영 상한입니다. 목적은 스레드풀과 DB 보호입니다. 시트별 상한을 쓰고 합산 상한을 기각한 데에는 근거가 있습니다. 최대 루트 하나만 선택해도 약 236만 행으로 전개되기 때문에, 합산 상한은 정상적인 선택까지 차단합니다. hard stop은 상한의 110%인 22만 건입니다.
- **영구 워크테이블과 INSERT…SELECT 안의 Oracle CONNECT BY**: 전역 임시 테이블(GTT)은 커넥션 풀이 세션을 고정하지 않아 기각했고, 자바에서 트리를 순회하는 안은 전체 전개가 실측 약 3.5초라 필요하지 않았습니다. 스트리밍 대신 적재를 택한 핵심 이유는 정렬입니다. "철 분류번호 순서, 그 철 아래에 분권을 인터리브"하는 순서는 CONNECT BY의 행 산출 순서로 보장할 수 없어, 적재한 뒤 ROW_NUMBER()로 일괄 채번했습니다.
- **SXSSF와 1만 행 청크, .tmp 후 rename**: 기존 공통 엑셀 헬퍼는 고정 템플릿과 전량 List를 전제로 해서 쓸 수 없었습니다. 기존의 대량 처리 사례도 전량 List 적재 방식이라, 19개 이상 컬럼에 20만 건이면 수백 MB heap을 점유해 WAR로 올라가는 Tomcat에서 위험합니다. 1만이라는 청크 크기는 관례적으로 쓰는 값입니다. ROWNUM 페이징 대신 순번 범위 조회를 쓴 이유는 순번이 워크테이블에 고정되어 순서와 중복 문제가 없기 때문입니다. .tmp로 쓰고 완료 후 rename하는 것은 쓰다가 죽은 파일이 정상 완료 파일로 오인되는 것을 막기 위해서입니다.
- **전용 스레드풀 분리**: 공용 스레드풀은 다른 리스너와 공유되기 때문입니다. "동시 1건" unique index guard와 함께 묶은 보호 장치 중 하나입니다.
- **모든 상태 전이를 CAS로 처리**: 이 규칙이 없으면 사용자가 취소한 잡이 뒤늦게 완료로 되살아납니다. 취소도 조회 후 UPDATE가 아니라 단일 CAS 문으로 처리했습니다. 그 사이에 워커가 상태를 실행 중으로 바꾸면 취소한 줄 알았는데 실행되는 상태가 되기 때문입니다.
- **복구 수단**: 1시간을 넘긴 실행 중 작업을 실패로 돌리는 sweeper는 기존 배치의 방식을 따랐고, 주 복구 수단은 애플리케이션 기동 시 동작하는 리스너입니다. 30일 경과 파일 삭제는 저장 볼륨 문제에 대한 대응이며 30일이라는 값은 관례적으로 정했습니다.

#### 수행 내용

- 신청, 승인, 반영 공통 파이프라인 설계와 구현
- 전거 일괄 등록, 철·건 일괄 수정, 신청 관리, 승인 관리, 헤더 알림 화면 개발
- 관계전거를 즉시 반영에서 승인제로 전환, 6개 유형별 팝업을 반복하던 흐름을 다중선택 1회로 변경, 헤더 알림에서 해당 행으로 자동 이동
- 데이터 추출: 조건 필터, 계층 트리 추출, 백그라운드 잡 큐, SXSSF 청크 엑셀 생성
- 메뉴·권한 등록 SQL을 환경 독립적·idempotent하게 작성
- 성능 진단: 8건 추출에 245초가 걸리던 문제를 로그로 분해해 거의 전부가 단일 쿼리에서 발생함을 확인했고, 신규 워크테이블의 통계가 없어 대용량 테이블 full scan이 일어나고 있었습니다. 통계 수집 후 1~3초로 떨어졌고 통계를 고정해 자동 수집에 의존하지 않게 했습니다. 이 과정에서 대형 테이블의 통계가 수년간 갱신되지 않은 상태임을 확인했습니다.
- 기록건 미리보기 응답 개선: 키를 정렬한 뒤 본문을 조회하는 2단계로 분리
- 데이터 상태 문제 대응: 핵심 테이블의 soft delete 컬럼이 전부 NULL이었고 계층이 끊어진 행이 있어 INNER JOIN을 쓰면 조용히 누락됐습니다. LEFT JOIN을 강제했습니다.
- 타입 변환 실수 하나가 만든 세 가지 증상 수정: 공통코드 캐시가 UUID를 코드 문자열로 바꿔 넣어 역방향 행에 잘못된 값이 INSERT되고, 중복검사가 동작하지 않아 승인할 때마다 잘못된 데이터가 쌓이며, 삭제는 항상 0행이 처리됐습니다. 일괄 경로는 정상이고 단건 팝업만 문제가 있어 둘을 비교해 원인을 찾았습니다. 잘못된 데이터 정리 SQL(백업, 조사, 매핑, 조건부 UPDATE, 대조 검증)을 작성했으며 실행은 하지 않은 상태입니다.

#### 업무 성과

- 개발자가 SQL로 직접 처리하던 전거·기록물 대량 수정을 담당자가 화면에서 신청하고 관리자가 승인하면 반영되는 흐름으로 바꿔, 개발자 개입 없이 처리되게 했습니다.
- 승인 처리 구조를 재사용 가능하게 만들어, 후속 화면인 신청 관리를 신규 SQL과 매퍼 없이 설정 한 줄 추가로 구현했습니다.
- 기존 수작업 SQL이 누락하던 4,074건(부모 철만 조건에 맞는 분권)을 추출 결과에 정확히 포함시켰습니다.
- 8건 추출에 245초가 걸리던 문제를 통계 부재로 인한 full scan으로 특정해 1~3초로 줄였고, 통계를 고정해 재발하지 않게 했습니다.
- 기록건 미리보기 응답을 27.9초에서 2.3초로 줄였습니다.
- 단위테스트를 34건에서 64건으로 늘렸습니다.
- 데이터 추출 기능은 검수 대기 상태로 아직 운영에 반영되지 않았고, 잘못된 데이터 정리 SQL은 작성만 되어 있습니다.

| 항목 | 내용 |
|---|---|

#### 프로젝트 설명

개발팀의 배포 방식과 소스 관리 환경을 재구축했습니다.

#### 배경과 문제

배포가 수동이라 한 번에 20분에서 1시간이 걸렸고 휴먼 에러가 잦았습니다. 개발 환경은 로컬에 묶여 있었고, 소스 백업 체계가 없었습니다.

#### 기술 선택과 근거

- **Docker 표준화**: 로컬 의존성 때문에 개발, 스테이징, 프로덕션 환경이 서로 달라지는 문제를 없애기 위해서입니다.
- **GitLab과 Jenkins 온프레미스 자체 구축**: 하드웨어 유통과 솔루션을 다루는 회사라 사내 서버를 확보하기 쉬웠습니다. 클라우드 비용 없이 내부망에서 소스와 빌드를 관리할 수 있었습니다.
- **MS Teams 알림**: 회사 표준 협업 도구라 별도 도구를 추가하지 않았습니다.
- **표준 문서화**: 프레임워크·애플리케이션 문서와 개발 환경 설정 매뉴얼로 온보딩 시간을 줄였고, Git 브랜치 전략과 커밋 메시지, DB 네이밍 컨벤션을 정해 컨벤션이 없어서 생기던 작업 복잡도와 커뮤니케이션 문제를 줄였습니다.

#### 수행 내용

- Docker 컨테이너 환경 표준화
- GitLab과 Jenkins 온프레미스 구축, Webhook 기반 CI/CD 파이프라인으로 빌드·배포 자동화
- 저장소 자동 백업·모니터링과 MS Teams 알림 연동
- 표준 문서화 프로세스와 Git·DB 컨벤션 정립

#### 업무 성과

- 수동으로 20분~1시간 걸리던 배포를 파이프라인으로 자동화해 10분으로 줄였습니다.
- 로컬에 묶여 있던 개발 환경을 Docker로 표준화해 개발·스테이징·프로덕션 환경 차이로 생기던 문제를 없앴습니다.
- 백업 체계가 없던 소스 저장소에 자동 백업과 모니터링을 붙여 소스 보존율 99.9%를 유지했습니다.
- 표준 문서와 Git·DB 컨벤션을 정립해 신규 입사자 온보딩 시간을 줄이고, 컨벤션이 없어서 생기던 커뮤니케이션 문제를 줄였습니다.

### 3.8 대학교 웹 솔루션 개발

| 항목 | 내용 |
|---|---|
| 기간 | 2024.05 ~ 2024.08 |
| 소속 | 에듀에듀 개발사업팀 |
| 역할 | 인증 체계와 성능 개선 담당 |
| 사용 기술 | Java, Spring, JSP, MyBatis, JWT, Redis, MySQL |

#### 프로젝트 설명

대학 웹 플랫폼의 인증 체계와 성능을 개선했습니다.

#### 배경과 문제

인증이 단일 토큰 방식이라 토큰이 탈취되면 만료 전까지 대응할 방법이 없었습니다. 또 반복적인 DB 조회 때문에 페이지 로드가 1초를 넘었습니다.

#### 기술 선택과 근거

- **JWT Access + Refresh Token**: 수명이 짧은 Access 토큰과 재발급용 Refresh 토큰으로 분리해 탈취 시 피해 범위를 제한했습니다.
- **Refresh Token을 Redis에 보관**: 이후 서버를 스케일 아웃할 때 인스턴스 간에 토큰을 공유할 수 있어야 했습니다.
- **정적 데이터 Redis 캐싱**: 반복적인 DB 조회가 로드 지연의 원인이었습니다.
- **AOP 기반 로깅**: 각 화면 코드를 수정하지 않고 CRUD 이벤트와 방문 기록을 일괄 수집하기 위해서입니다.
- **RESTful API 구조**: 20건 이상의 신규 요구사항을 구조 변경 없이 반영할 수 있었습니다.

#### 수행 내용

JWT Access와 Refresh Token 이중 인증·인가, Redis 기반 토큰 관리와 정적 데이터 캐싱, AOP 기반 전사 페이지 로깅 시스템을 구현했고, RESTful API 구조로 신규 요구사항 20건 이상을 반영했습니다.

#### 업무 성과

- 단일 토큰 인증을 Access·Refresh 이중 구조로 바꿔 토큰이 탈취돼도 피해 범위가 제한되게 했습니다.
- 반복되던 DB 조회를 Redis 캐싱으로 줄여 페이지 로드 시간을 1,000ms에서 300~400ms로 단축했습니다.
- 화면 코드를 수정하지 않고 AOP로 전사 페이지 로그를 수집하게 해 사용자 행동 분석 기반을 만들었습니다.
- RESTful API 구조로 신규 요구사항 20건 이상을 구조 변경 없이 반영했습니다.
